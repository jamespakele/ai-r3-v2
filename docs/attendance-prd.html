01. Overview

Attendance Tracking: Calendar Matrix + Event Sessions

A unified design combining the Calendar Matrix (Approach #2) as the primary attendance view with Event Sessions (Approach #3) for program lifecycle management and funder reporting.

Executive Summary: This feature adds attendance tracking to the R3 Intake system. Coordinators record daily participant check-ins using a spreadsheet-style matrix grid (participants × dates). An optional Events layer groups dates into named program cycles (e.g., "Summer Outreach 2026") for reporting. The matrix works with or without events — events are an organizational layer, not a prerequisite.
Key principle: The Calendar Matrix is the primary attendance view. Events are opt-in. Coordinators can check people in Day 1 without creating any events. When an admin creates an event and enrolls participants, the matrix simply adds an event filter dropdown and shows enrollment-aware rosters.

Problem Statement

R3 coordinators currently track attendance manually (paper sign-in sheets, spreadsheets). Challenges:

  • No centralized record of who attended which outreach sessions
  • Difficulty identifying participants who have stopped engaging
  • Time-consuming to compile attendance reports for funders or board meetings
  • No way to see attendance patterns over time
  • Walk-in participants cannot be easily tracked or later connected to intake records

Proposed Solution

A dedicated Attendance tab in the R3 Intake app with three screens:

  1. Admin: Event Management — Create multi-week program cycles tied to a location and date range. Enroll participants from existing intake records.
  2. Calendar Matrix — Spreadsheet grid: participants as rows, dates as columns. Color-coded dots for present/absent/excused/walk-in. Click to toggle. CSV export.
  3. Per-Person Calendar — Mobile-optimized monthly calendar for a single participant's attendance history.
02. Goals & Success Metrics

What Success Looks Like

Primary Goals

  • Record daily attendance in under 30 seconds for 10 participants
  • Identify dropout participants within 2 weeks of last attendance
  • Generate funder-ready attendance reports with one click (CSV export)
  • Track walk-ins and link them to existing intake records later
  • Organize attendance by program cycle for reporting periods

Success Metrics

  • Adoption: 100% of outreach sessions logged within 4 weeks
  • Speed: Average check-in time <3 seconds per participant
  • Data Quality: <5% duplicate or erroneous records
  • Reporting: Zero manual data compilation for monthly reports
Non-Goals (Out of Scope for V1): QR code check-in, geofencing, automated reminders, participant self-service portal, HMIS integration, sub-activities within events.

04. User Stories

Who Does What and Why

Outreach Coordinator (Case Manager)
As a coordinator, I want to quickly check in participants at each outreach session using the matrix, so that we have an accurate record of who attended.
Acceptance Criteria:
  1. Opens Attendance tab → sees matrix filtered to today's date column
  2. Taps a dot to toggle: empty → present → absent → excused → walk_in → empty
  3. Can add optional note per participant
  4. Auto-saves via HTMX (no explicit save button needed)
  5. Takes <30 seconds for 10 participants
Program Administrator
As an admin, I want to create and manage multi-week outreach programs (events), so that attendance is organized by program cycle for reporting.
Acceptance Criteria:
  1. Can create event with name, location, start/end dates, description
  2. Can enroll participants from existing intake records (search by name)
  3. Can view enrolled roster with attendance stats (days attended, rate %)
  4. Can mark event as "completed" when program cycle ends
  5. Can view completed event summary report
Outreach Coordinator (Case Manager)
As a coordinator, I want to see a calendar matrix of attendance over weeks, so that I can spot who's been coming regularly and who's stopped showing up.
Acceptance Criteria:
  1. Can filter matrix by event, site, and date range
  2. Sees participants as rows, dates as columns with color-coded dots
  3. Dropout rows highlighted with red background + "STOPPED" badge
  4. Can click any cell to toggle attendance status
  5. Can export matrix as CSV
Case Manager
As a case manager, I want to view a single participant's attendance history as a calendar, so that I can discuss their engagement patterns during case management meetings.
Acceptance Criteria:
  1. Opens intake record → clicks Attendance tab
  2. Sees monthly calendar with present/absent/excused days
  3. Shows total days, present count, rate %, current streak
  4. Can navigate to prev/next month
  5. Can click a day to see detail (event, recorded by, time, note)
Program Administrator
As an admin, I want to export attendance data for a given event or date range, so that I can include it in funder reports or board presentations.
Acceptance Criteria:
  1. Can export CSV with columns: date, participant, site, event, status, recorded by, note
  2. Can filter export by event, date range, or site
  3. CSV includes summary stats row (total check-ins, unique participants, avg rate)

Key Constraints & Rules

Unique constraintOne attendance record per (event, intake, date). If event is null, unique per (intake, site, date). Enforced in Go handler (PocketBase has no native unique constraints).
Nullable eventThe event field on attendance is required: false. This allows the matrix to work Day 1 without any events created.
Walk-in statusstatus = "walk_in" means participant was not enrolled in the event (or no event selected). Can be converted to enrolled after the fact.
Cascade deleteDelete event → cascade delete enrollments + attendance. Delete intake → cascade delete enrollment + attendance. Delete site → restricted.
EnrollmentJunction table. Soft delete on unenroll (keeps attendance history). Many-to-many: participants can be in multiple events.

12. Risks & Mitigations

What Could Go Wrong

Risk: Low Adoption
Coordinators continue using paper sign-in sheets.

Mitigation: 5-minute training demo. Pre-load events. Make matrix the default landing for coordinators.
Risk: Data Entry Errors
Wrong participant marked present, or wrong date.

Mitigation: Today's column highlighted. "Undo" via clicking dot back to empty. Audit trail in recorded_by + timestamps.
Risk: Performance with Large Datasets
Matrix slows with 100+ participants × 60+ dates.

Mitigation: Default 14-day window. Limit to 30 days max. Pagination for longer ranges.
Risk: Privacy
Attendance data could be sensitive if exposed.

Mitigation: All PB rules null (Go is policy layer). Session auth required. Site-scoped access for case managers.

15. Decision Log

Key Design Decisions

Why Matrix over Daily Roster?Matrix gives pattern visibility (dropouts, trends) in one view. Daily roster is a subset — filter the matrix to one date column. Matrix serves both coordinator (daily) and director (weekly) without separate screens.
Why nullable event on attendance?Allows matrix to work Day 1 without any events created. Events are opt-in, not a prerequisite.
Why walk_in status instead of boolean?Preserves "came but not enrolled" vs "enrolled and present." Four-state cycle covers all real-world cases. Enables walk-in conversion tracking.
Why junction table for enrollment?Many-to-many: participants can be in multiple events. Enrollment date tracks when they joined. Soft delete preserves attendance history on unenroll.
Why HTMX for cell toggles?Matches existing stack. No new dependencies. Works without JS (full page reload fallback). Instant feedback, server-authoritative.
Why sticky participant column?Essential for horizontal scroll on matrix. Pure CSS, no JS needed.
Why not PocketBase views for summary?Go handler computes summaries on read — simpler, no sync issues. Can add materialized view later if performance needs it.
16. Open Questions

Decisions Needed Before Development

  • Should walk-ins be allowed without any intake record? Current design: yes, with name-only minimal record. Alternative: require intake first.
  • Should coordinators be able to edit attendance after save? Current design: yes, click dot to cycle back. Alternative: lock after 24 hours.
  • Auto-create events for each site? Current design: optional seed migration creates one active event per site. Alternative: require manual event creation.
  • Matrix shows only enrolled participants, or all intake records at site? Current design: enrolled only when event selected; all site participants when no event. Alternative: toggle.
  • Should we add check-out time? Current design: check-in time only. Alternative: add check-out for duration tracking (not V1).
Recommendation: Decide these in kickoff meeting. Default to simplest option if unclear. Update this section with decisions.
